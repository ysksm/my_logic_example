Chrome DevTools ガイド

ソースマップで
「元のコード」をデバッグする

本番のJavaScriptは圧縮・変換されていて読めない。ソースマップを使えば、DevTools 上で自分が書いたコードのままデバッグできます。

要素コンソールソースネットワークパフォーマンス 
// デプロイされたファイル(実際に実行されるもの)
const t=document.querySelector("#a");t.addEventListener("click",()=>{...});
//# sourceMappingURL=app.min.js.map

02なぜソースマップが必要か

パフォーマンスのため、本番コードは圧縮・結合・変換されます。その結果、ブラウザで動くコードは人間には読めません。

作成したコード(開発時) 
const button = document
  .querySelector("#submit");

button.addEventListener("click", () => {
  validateForm();
});
デプロイされたコード(本番) 
const e=document.querySelector("#submit");e.addEventListener("click",()=>{v()});

変数名は短縮され、改行・空白は削除。エラー行番号も元コードと一致しない。

解決策:ソースマップが「圧縮後のコード」と「元のコード」の対応表になり、DevTools が元のコードを表示・デバッグできるようにします。Chrome が実際に実行するのはあくまで圧縮コードです。

03仕組み — DevTools はどうやって元コードを表示するのか

app.min.js
デプロイされたファイル。末尾に //# sourceMappingURL コメントを含む
→
app.min.js.map
ソースマップ本体。圧縮コードの各位置 → 元ファイルの位置の対応表
→
ソースパネルに元コードを表示
ブレークポイント・エラー・コンソールログが元のファイル/行に自動でマッピングされる
// デプロイされたファイルの末尾
//# sourceMappingURL=app.min.js.map
注:DevTools はデプロイされたファイルからこのコメントを検出すると通知します。前提は2つ — ソースマップを生成できるビルドツールを使うこと、ウェブサーバーがソースマップを配信できること。

04ソースマップを生成できるツール

主要なプリプロセッサ/ビルドツールはすべてソースマップの出力に対応しています。

トランスパイラ

Babel

新しい構文を古い環境向けの JavaScript に変換

コンパイラ

TypeScript / Dart

別言語から JavaScript を生成

圧縮ツール

terser

変数名の短縮・空白削除でサイズを最小化

バンドラー

Webpack / Vite / esbuild / Parcel

複数ファイルを結合して配信用にビルド

ヒント:ほとんどのツールは設定1つで有効化できます(例: devtool: "source-map"、sourceMap: true)。

05DevTools でソースマップを有効にする

  1. DevTools を開き、設定(⚙) > [設定] > [ソース] を開く
  2. [JavaScript ソースマップを有効にする] がオンになっていることを確認 デフォルトで有効
  3. [CSS ソースマップを有効にする] もオンにするのがおすすめ(Sass などの元ファイルが見える)
確認方法:ソースマップが正しく読み込まれたかは [デベロッパー リソース] パネルで確認できます。読み込みの失敗もここに表示され、手動で読み込むこともできます。

06ソースマップを使ったデバッグの流れ

  1. [ソース] パネルでサイトのソースを開き、[作成者](Authored)セクションから元のソースファイルを開く — デプロイ済みファイルは [デプロイ済み] セクションに並ぶ
  2. 元のコードに通常どおりブレークポイント(ログポイントも可)を設定する
  3. コードを実行すると、一時停止・エラー・コンソール出力はすべて元のファイルの行番号で表示される
  4. [コールスタック] ペインにも元のファイル名が表示される
  5. エディタ下部のステータスバーのリンクから、対応するデプロイ済みファイル(圧縮コード)側の位置へジャンプできる

07おまけ: #sourceURL で eval() に名前を付ける

eval() や new Function() で動的に生成したコードは、通常ファイル名を持たずデバッグしづらい。#sourceURL コメントで仮想的なファイル名を付けられます。

コード 
eval(`
  console.log("hello");
  //# sourceURL=myScript.js
`);
結果

[ソース] パネルのファイルツリーに myScript.js として表示され、ブレークポイントの設定やスタックトレースでの参照が可能になる。

sourceMappingURL とよく似た仕組みで、動的コードのデバッグを簡素化するヘルパー。

08まとめ

  • 本番コードは圧縮されて読めない → ソースマップが圧縮コードと元コードを対応付ける
  • Chrome が実行するのは圧縮コード。表示とデバッグ体験だけが元コードになる
  • Babel / TypeScript / terser / Webpack / Vite など主要ツールはすべて対応
  • DevTools 設定で JavaScript / CSS ソースマップをオンに(デフォルト有効)
  • [作成者] セクションの元ファイルにブレークポイントを置けば、エラーもログも元の行番号で追える
  • 動的コードには //# sourceURL=名前.js で名前を付ける
