STEP 07

CORS 応用 ── プリフライト・ヘッダー・Cookie

実際の API 開発でハマるポイントを、ブラウザ側とサーバー側のコードを並べて確認します。

1. 単純リクエストとプリフライトリクエスト

「サーバーに副作用を与えうる」リクエストの場合、ブラウザは本番のリクエストの前に OPTIONS で 「これ送っていい？」と事前確認（プリフライト） します。

単純リクエスト
（プリフライトなし）		メソッドが GET / HEAD / POST のどれか
かつ 独自ヘッダーなし（Accept, Content-Type など一部のみ）
かつ Content-Type が text/plain / application/x-www-form-urlencoded / multipart/form-data
プリフライトあり上記以外すべて。例: PUT / DELETE / PATCH、Content-Type: application/json、Authorization や X-Xxx ヘッダー
ブラウザ                                                   API サーバー
  │ fetch(url, { method: "PUT", headers: { "X-Demo-Token": "abc" } })
  │
  │ ── OPTIONS /advanced/preflight-ok ──────────────────────▶ │ ① プリフライト
  │    Origin: http://localhost:3000                            │
  │    Access-Control-Request-Method: PUT                       │

  │    Access-Control-Allow-Origin: http://localhost:3000       │

  │ ── PUT /advanced/preflight-ok ──────────────────────────▶ │ ② 本番リクエスト
  │ ◀── 200 + Access-Control-Allow-Origin ───────────────────── │

2. 実験

A. POST + text/plain 単純

fetch(API + "/advanced/preflight-ok", {
  method: "POST",
  headers: { "Content-Type": "text/plain" },
  body: "hello",
});

B. POST + application/json プリフライト

fetch(API + "/advanced/preflight-ok", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ hello: "world" }),
});

C. PUT + 独自ヘッダー（サーバーが許可）プリフライト

fetch(API + "/advanced/preflight-ok", {
  method: "PUT",
  headers: { "X-Demo-Token": "abc123" },
});

D. PUT + 独自ヘッダー（サーバーが不許可）失敗例

fetch(API + "/advanced/preflight-ng", {
  method: "PUT",
  headers: { "X-Demo-Token": "abc123" },
});

→ ログを見ると OPTIONS だけ 届いていて、PUT は 送られていない。STEP 6 の B（送られたが読めない）との違いに注目。

3. Cookie を送る（credentials）

別オリジンへの fetch は、標準では Cookie を送らないし、受け取った Set-Cookie も保存しない。送りたいときはクライアントとサーバーの両方で明示的に許可します。

クライアントfetch(url, { credentials: "include" })
サーバーAccess-Control-Allow-Credentials: true
Access-Control-Allow-Origin は * 不可。具体的なオリジンを返す

②は session が返る。③は Cookie が送られないので null。④は「Allow-Origin が * なのに credentials」でブラウザが拒否。
※ localhost:3000 と localhost:4000 は「別オリジン」だが「同一サイト」なので、SameSite=Lax の Cookie でも送られます。本当に別ドメインの場合は SameSite=None; Secure（HTTPS 必須）が必要です。

4. 実務で使える CORS ミドルウェア（Node.js 標準モジュールのみ）

ここまでのルールを 1 つの関数にまとめたものです。Express の cors パッケージが内部でやっていることとほぼ同じです。

const ALLOWED_ORIGINS = new Set(["http://localhost:3000", "https://app.example.com"]);

function applyCors(req, res) {
  const origin = req.headers.origin;

  // Origin によってレスポンスが変わるので、CDN やブラウザのキャッシュに伝える
  res.setHeader("Vary", "Origin");

  // ① 許可リストにないオリジン（または Origin なし = 同一オリジンや curl）には何も付けない
  if (!origin || !ALLOWED_ORIGINS.has(origin)) return false;

  // ② 許可するオリジンをそのまま返す（credentials を使うなら * は使えない）
  res.setHeader("Access-Control-Allow-Origin", origin);
  res.setHeader("Access-Control-Allow-Credentials", "true");
  res.setHeader("Access-Control-Expose-Headers", "X-Total-Count");

  // ③ プリフライトなら、許可するメソッド・ヘッダーを返して終了（本番の処理はしない）
  if (req.method === "OPTIONS") {
    res.setHeader("Access-Control-Allow-Methods", "GET, POST, PUT, PATCH, DELETE");
    res.setHeader("Access-Control-Allow-Headers", "Content-Type, Authorization");
    res.setHeader("Access-Control-Max-Age", "600");  // 10 分キャッシュ（Chrome の上限は 2 時間）
    res.writeHead(204);
    res.end();
    return true;  // ← 呼び出し側はここで処理を打ち切る
  }
  return false;
}

http.createServer((req, res) => {
  if (applyCors(req, res)) return;  // プリフライトはここで終わり
  // … 通常のルーティング …
});

このサンプルの各エンドポイントの実装は server.js の apiRoutes にあります。わざと失敗させるもの（preflight-ng, me-wildcard）も含めて読み比べてみてください。

5. よくあるエラーと対処

No 'Access-Control-Allow-Origin' header is presentサーバーが ACAO を返していない。エラー時（500 など）のレスポンスにも付け忘れていないか確認
Response to preflight request doesn't pass access control checkOPTIONS に応答していない / 認証ミドルウェアが OPTIONS を 401 にしている。OPTIONS は認証より前に処理する
Request header field x-xxx is not allowed by Access-Control-Allow-Headers独自ヘッダーを Access-Control-Allow-Headers に追加する
The value of the 'Access-Control-Allow-Origin' header must not be the wildcard '*' when the request's credentials mode is 'include'credentials を使うなら ACAO に具体的なオリジンを返す
