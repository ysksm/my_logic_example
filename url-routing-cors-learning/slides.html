STEP 02 · クエリパラメーター

画面の状態を URL に置くと、リロードしても共有しても再現できる

// 読み込み時: URL → 画面
const p = new URLSearchParams(location.search);
cat.value = p.get("cat") ?? "";

// 変更時: 画面 → URL
cat.addEventListener("input", () => {
  const p = new URLSearchParams(location.search);
  cat.value ? p.set("cat", cat.value) : p.delete("cat");
  history.replaceState(null, "", "?" + p);
  render();
});
replaceState を使う理由

絞り込みを変えるたびに履歴が増えると「戻る」が使いにくい。履歴を増やしたいなら pushState。

入れてはいけないもの

パスワードやトークン。URL は履歴・サーバーログ・Referer に残る。

STEP 03 · サーバーサイドルーティング

パスを見て、サーバーが返す HTML を決める

ブラウザ                                       server.js
  │ <a href="/server/items/2"> をクリック            │
  │ ─── GET /server/items/2 ─────────────────────▶ │  /server            ✗
  │                                                │  /server/items      ✗
  │                                                │  /server/items/:id  ✓ → params.id = "2"
  │ ◀── 200 OK + HTML（ページ全体）─────────────── │
  │ 画面をまるごと描き直す（フルリロード）
良い点

単純。JS なしで動く。どの URL でもリロード・ブックマーク・検索エンジンが効く。

弱い点

遷移のたびに通信して画面全体を作り直す。入力中の状態や JS の変数は消える。

STEP 03 · サーバーサイドルーティング

ルーティングの正体は「パターン照合の表」

const serverRoutes = [
  { method: "GET", pattern: "/server",           handler: serverHome },
  { method: "GET", pattern: "/server/items/:id", handler: serverItemDetail },
];

function matchRoute(pattern, pathname) {        // "/server/items/:id" vs "/server/items/2"
  const p = pattern.split("/").filter(Boolean);
  const a = pathname.split("/").filter(Boolean);
  if (p.length !== a.length) return null;
  const params = {};
  for (let i = 0; i < p.length; i++) {
    if (p[i].startsWith(":")) params[p[i].slice(1)] = decodeURIComponent(a[i]);  // → { id: "2" }
    else if (p[i] !== a[i]) return null;
  }
  return params;
}
// どれにもマッチしなければ 404。クエリは url.searchParams.get("q") でサーバーでも読める

Express の app.get("/items/:id", …) も、React Router の <Route path="/items/:id"> も同じ考え方。この matchRoute は STEP 4・5 のブラウザ側でもそのまま使い回しています。

STEP 04 · ハッシュルーティング

# 以降はサーバーに届かない → ブラウザだけで画面を切り替える

const routes = [
  { pattern: "/",          view: homeView },
  { pattern: "/users/:id", view: userDetailView },
];

function router() {
  // "#/users/2?tab=a" → path "/users/2", query "tab=a"
  const raw = location.hash.slice(1) || "/";
  const [path, q = ""] = raw.split("?");
  const query = new URLSearchParams(q);
  for (const r of routes) {
    const params = matchRoute(r.pattern, path);
    if (params) return render(r.view(params, query));
  }
  render(notFoundView());
}
window.addEventListener("hashchange", router);
router();   // 初回（リロード時）も忘れずに
良い点

サーバー設定ゼロ。静的ホスティングや file:// でも動く。リロードしても 404 にならない。

弱い点

URL に # が入る。サーバーはパスを知らないので SSR・SEO に不利。ページ内リンクと衝突。

STEP 06 · CORS の基本

ブラウザは「別オリジンのレスポンスを JS で読む」ことを禁止している

これが 同一オリジンポリシー。サーバーが「このオリジンなら読んでいいよ」とヘッダーで許可する仕組みが CORS（Cross-Origin Resource Sharing）。

localhost:3000 のページから見て判定理由
http://localhost:3000/api/hello同一オリジンパスが違うだけ
http://localhost:4000/basic/…別オリジンポートが違う（このサンプルの API）
http://127.0.0.1:3000/別オリジン同じマシンでも文字列が違う
https://localhost:3000/別オリジンプロトコルが違う

STEP 06 · CORS の基本

違いはレスポンスヘッダー 1 行だけ

// server.js（API サーバー :4000）
"/basic/no-cors":  () => ({ headers: {} }),

"/basic/wildcard": () => ({ headers: {
  "Access-Control-Allow-Origin": "*" } }),

"/basic/allowlist": (req) => {
  const o = req.headers.origin;   // ブラウザが自動で付ける
  return ALLOWED.has(o)
    ? { headers: { "Access-Control-Allow-Origin": o,
                   Vary: "Origin" } }
    : { headers: { Vary: "Origin" } };
},
実験JS で読める？
A. 同一オリジン✓ 読める
B. ACAO なし✗ TypeError: Failed to fetch
C. ACAO: *✓ 誰でも読める
D. ACAO: 許可リスト✓ 許可オリジンだけ
mode: "no-cors"エラーにならないが中身は空（opaque）

JS 側から見えるのは「失敗した」ことだけ。理由は DevTools の Console にしか出ない（攻撃者に情報を渡さないため）。

STEP 06 · CORS の基本

ブロックされても、リクエストはサーバーに届いている

ブラウザ (:3000)                         API (:4000)
  │ ── GET /basic/no-cors ───────────────▶ │
  │    Origin: http://localhost:3000        │ 処理される
  │ ◀── 200 OK（ACAO なし）─────────────── │ ログにも残る
  │
  │ ブラウザ「許可がないので JS に渡さない」
誤解しやすい点

CORS はサーバーを守らない

ブラウザが「レスポンスを JS に渡すか」を決めるだけ。curl なら普通に取れる。認証・CSRF 対策は別途必要。

STEP 6 のページには API サーバーの受信ログが表示されるので、B を実行して「失敗なのにサーバーには届いている」ことを自分の目で確認できます。

STEP 07 · CORS 応用

プリフライト: 本番の前に OPTIONS で「送っていい？」と聞く

単純リクエスト（プリフライトなし）

GET / HEAD / POST のどれか
＋ 独自ヘッダーなし
＋ Content-Type が text/plain・form-urlencoded・multipart/form-data

プリフライトあり

それ以外すべて。
PUT / DELETE / PATCH、Content-Type: application/json、Authorization や X-Xxx ヘッダー

── OPTIONS /advanced/preflight-ok ─────────▶   Access-Control-Request-Method: PUT
                                                Access-Control-Request-Headers: x-demo-token
◀── 204 ───────────────────────────────────   Access-Control-Allow-Origin: http://localhost:3000
                                                Access-Control-Allow-Methods: GET, POST, PUT, DELETE
                                                Access-Control-Allow-Headers: Content-Type, X-Demo-Token
                                                Access-Control-Max-Age: 0   ← 結果のキャッシュ秒数（学習用に 0）
── PUT /advanced/preflight-ok ─────────────▶   （許可されたので本番を送る）

STEP 07 · CORS 応用

プリフライトで断られると、本番リクエストは送られない

ケースサーバーに届くものJS の結果
STEP 6-B：単純リクエスト・ACAO なしGET が届いて処理される失敗（読めないだけ）
STEP 7-C：PUT + X-Demo-Token・許可ありOPTIONS → PUT成功
STEP 7-D：PUT + X-Demo-Token・ヘッダー不許可OPTIONS だけ（PUT は来ない）失敗
だから「副作用のある操作は PUT / DELETE / JSON で受ける」と、許可していないオリジンからの変更をブラウザが事前に止めてくれる。逆に単純リクエストの POST は届いてしまうので、CSRF トークン等で守る。

よくある事故: 認証ミドルウェアが OPTIONS にも認証を要求して 401 を返し、プリフライトが失敗する。OPTIONS は認証より前で処理する。

STEP 07 · CORS 応用

ヘッダーを読む・Cookie を送るには、さらに明示的な許可が必要

レスポンスヘッダーの公開 
// サーバー
"X-Total-Count": "42",
"Access-Control-Expose-Headers": "X-Total-Count",

// ブラウザ
res.headers.get("X-Total-Count") // "42"
res.headers.get("X-Request-Id")  // null

標準で読めるのは Content-Type など一部だけ。

Cookie（credentials） 
// ブラウザ
fetch(url, { credentials: "include" });

// サーバー
"Access-Control-Allow-Origin": origin, // * は不可
"Access-Control-Allow-Credentials": "true",

両方そろって初めて Cookie が送受信される。ACAO: * + include はブラウザが拒否。

本当に別ドメインの Cookie は SameSite=None; Secure（HTTPS 必須）も必要。サンプルの localhost:3000 → :4000 は「別オリジンだが同一サイト」なので Lax でも送られる。

STEP 07 · CORS 応用

実務用: CORS ミドルウェアの全体像

function applyCors(req, res) {
  const origin = req.headers.origin;
  res.setHeader("Vary", "Origin");                               // Origin で結果が変わることをキャッシュに伝える
  if (!origin || !ALLOWED_ORIGINS.has(origin)) return false;     // ① 許可リスト外には何も付けない

  res.setHeader("Access-Control-Allow-Origin", origin);          // ② 具体的なオリジンを返す
  res.setHeader("Access-Control-Allow-Credentials", "true");
  res.setHeader("Access-Control-Expose-Headers", "X-Total-Count");

  if (req.method === "OPTIONS") {                                // ③ プリフライトはここで完結
    res.setHeader("Access-Control-Allow-Methods", "GET, POST, PUT, PATCH, DELETE");
    res.setHeader("Access-Control-Allow-Headers", "Content-Type, Authorization");
    res.setHeader("Access-Control-Max-Age", "600");
    res.writeHead(204).end();
    return true;
  }
  return false;
}
http.createServer((req, res) => { if (applyCors(req, res)) return; /* ルーティング */ });

開発中に CORS を避けたいだけなら、Vite の server.proxy などで API を同一オリジンに見せるのが定番。
