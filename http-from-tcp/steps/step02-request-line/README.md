# step02: リクエストラインを読む

## step01からの差分

- 受信テキストの**1行目だけ**を空白で3分割する
- **HTTPの応答テキストを手書き**して返す（これで初めて「HTTPサーバ」になる）

## 起動

```sh
node server.js
```

## 実験1 — 初めてのHTTP応答

```sh
curl -v http://localhost:8080/hello
```

ブラウザ `http://localhost:8080/` でも、今度はちゃんと文字が表示されます。
step01 との違いはたった数行の文字列です。

## 実験2 — メソッドは自由に名乗れる

```sh
curl -v -X POST http://localhost:8080/anything
curl -v -X DELETE http://localhost:8080/users/1
curl -v -X BANANA http://localhost:8080/
```

`BANANA` すら通ります。

**わかること:** メソッドはただの文字列。意味を与えるのはサーバ側の実装です。

## 実験3 — 空行を消すとどうなるか（重要）

`server.js` の `responseHead` の最後の `"\r\n"` を消して再起動し、`curl -v` してみてください。

```
* Empty reply from server
```

あるいは curl がずっと待ち続けます。

**わかること:** `\r\n\r\n`（空行）がヘッダーの終わりの唯一の目印。
これがないと、クライアントは「ヘッダーがまだ続く」と思って待ち続けます。

確認したら元に戻してください。

## 実験4 — 手で1リクエスト打ってみる

```sh
printf 'GET /manual HTTP/1.1\r\nHost: localhost\r\n\r\n' | nc localhost 8080
```

`printf` で `\r\n` を明示的に書いています。これが「HTTPを喋る」ということです。

## 用語

```
GET /hello?a=1 HTTP/1.1
└┬┘ └────┬───┘ └──┬───┘
 │        │        └── HTTPバージョン
 │        └────────── リクエストターゲット（パス＋クエリ）
 └─────────────────  メソッド
```

```
HTTP/1.1 200 OK
└──┬───┘ └┬┘ └┬┘
   │      │   └── 理由句（人間向け。ブラウザは見ない）
   │      └────── ステータスコード（機械が見るのはこれ）
   └───────────── HTTPバージョン
```

- なぜ改行が `\n` ではなく `\r\n` なのか？（ヒント: HTTPはテレタイプ時代の慣習を継いだテキストプロトコル）
- `Content-Length` を実際のボディ長より大きい値にしたら、curl はどうなるでしょう？（試してみてください）
