step03: ヘッダーをパースする

2行目以降を「名前: 値」に分解する。そのために「分割して届く」問題に向き合います。

このステップでわかること
  • ヘッダー名は大文字小文字を区別しない
  • 同名ヘッダーは , で連結する（Set-Cookie だけ例外）
  • 1回の data イベント ＝ 1メッセージ ではない
step02からの差分
  • 受信をバッファに溜める
  • \r\n\r\n が揃うまで待ってから解析する
  • ヘッダー名を小文字に正規化して辞書にする

なぜバッファに溜めるのか

TCPは「バイト列のストリーム」であって「メッセージの列」ではない サーバが1回 write したもの 受信側の data イベント ┌────────────────────────┐ ┌──────────┐ │ GET / HTTP/1.1\r\n │ │ GET / HT │ ← 1回目 │ Host: localhost\r\n │ ──→ ├──────────┤ │ X-Foo: 1\r\n │ │ TP/1.1\r │ ← 2回目 │ \r\n │ ├──────────┤ └────────────────────────┘ │ \nHost:… │ ← 3回目 └──────────┘ 逆に、2つのリクエストが1回の data でまとめて届くこともある
let buffer = Buffer.alloc(0);            // 接続ごとに用意

socket.on("data", (chunk) => {
  buffer = Buffer.concat([buffer, chunk]);  // まず溜める

  const headerEnd = buffer.indexOf("\r\n\r\n");
  if (headerEnd === -1) return;          // まだ揃っていない → 続きを待つ

  // ここから解析
});

ヘッダーの解析

const headText = buffer.subarray(0, headerEnd).toString("utf8");
const lines = headText.split("\r\n");

const [method, target, version] = lines[0].split(" ");   // 1行目

const headers = {};
for (const line of lines.slice(1)) {                     // 2行目以降
  const colon = line.indexOf(":");
  if (colon === -1) continue;                            // 壊れた行は無視

  // ヘッダー名は大文字小文字を区別しない（RFC 9110）
  const name  = line.slice(0, colon).trim().toLowerCase();
  const value = line.slice(colon + 1).trim();

  // 同名が複数回来たら "," で連結するのがHTTPの規則
  headers[name] = name in headers ? headers[name] + ", " + value : value;
}
なぜ小文字に揃えるのか

Content-Type / content-type / CONTENT-TYPE はすべて同じヘッダーです。 クライアントによって書き方が違うので、辞書に入れる時点で正規化しておくと、 以降のコードが headers["content-type"] だけを見ればよくなります。

cd steps/step03-headers
node server.js

実験1: curlとブラウザの差

curl http://localhost:8080/

curl は3〜4個。次にブラウザで開くと sec-ch-ua、 accept-encoding、sec-fetch-mode… と10個以上並びます。

実験2: 大文字小文字は区別されない

curl -H 'X-Foo: 1' -H 'x-FOO: 2' http://localhost:8080/

結果は x-foo : 1, 2 と1つにまとまります。

実験3: ヘッダーが分割して届く様子

{ printf 'GET /slow HTTP/1.1\r\n';
  sleep 1; printf 'Host: localhost\r\n';
  sleep 1; printf 'X-Late: yes\r\n';
  sleep 1; printf '\r\n'; } | nc localhost 8080

サーバに ▶ まだ \r\n\r\n が来ていません。続きを待ちます が何度か出てから、最後にまとめて解析されます。

実験4: Host ヘッダー

curl -H 'Host: example.com' http://localhost:8080/

接続先は localhost なのに host = example.com になります。

Host ヘッダーの役割

1つのIPアドレス・1つのポート │ ┌────────────┼────────────┐ │ │ │ example.com shop.com blog.example.com ↑ ↑ ↑ どれ宛のリクエストかを Host ヘッダーで見分ける

HTTP/1.1 で Host が必須になったのはこのためです。 1台のサーバで複数サイトを運用できます（バーチャルホスト）。

後の章への伏線

Host と、第4章で出てくる Origin は別物です。 Host は「どこ宛か」、Origin は 「どこから出たか」。step19 のプロキシでは Host を書き換えます。

クイズ: \r\n\r\n の直後から始まるのは何ですか？

ボディです。次のステップで扱います。 そしてそこで「ボディの終わりはどうやって知るのか」という難問に出会います。

クイズ: なぜ「壊れた行は無視」してよいのか？

学習用の割り切りです。実務のサーバは 400 Bad Request を返します。曖昧な入力を黙って受け入れると、 前段のプロキシと解釈がズレてリクエストスマグリングの温床になるためです。
