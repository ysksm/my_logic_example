step04: ボディを読む

TCPには「メッセージの終わり」がありません。ではボディはどこで終わるのか。

このステップの核心
  • ヘッダーの終わりには 印がある（\r\n\r\n）
  • ボディの終わりを示す印は存在しない
  • だから送信側が Content-Length で長さを先に宣言する

境界問題

ヘッダー部分 空行 ボディ ┌────────────────────┐ ┌──────┐ ┌───────────────┐ POST /json HTTP/1.1\r\n Content-Length: 21\r\n \r\n\r\n {"name":"太郎"} ↑ここから21バイト

接続は次のリクエストのために開いたままかもしれません。 「切断されたら終わり」では判断できないのです。

const bodyStart = headerEnd + 4;                       // "\r\n\r\n" の4バイト
const contentLength = Number(headers["content-length"] ?? 0);

if (buffer.length < bodyStart + contentLength) {
  return;   // まだ全部来ていない → 続きを待つ
}

const body = buffer.subarray(bodyStart, bodyStart + contentLength);
Content-Length はバイト数

文字数ではありません。 {"name":"太郎"} は「太郎」がUTF-8で6バイトなので21バイトです。 Buffer.byteLength() で数えてください。

手を動かす

cd steps/step04-body
node server.js

実験1: フォーム形式のPOST

curl -v -X POST -d 'name=taro&age=20' http://localhost:8080/form

curl が自動で Content-Length: 16 と Content-Type: application/x-www-form-urlencoded を付けています。

実験2: JSONのPOST

curl -v -X POST -H 'Content-Type: application/json' \
     -d '{"name":"太郎"}' http://localhost:8080/json

実験3: ボディが分割して届く様子

{ printf 'POST /slow HTTP/1.1\r\nHost: localhost\r\nContent-Length: 10\r\n\r\n';
  sleep 1; printf 'abcde';
  sleep 1; printf 'fghij'; } | nc localhost 8080
▶ ボディが足りません: 5 / 10 バイト。続きを待ちます

実験4: 嘘のContent-Lengthを送る

printf 'POST /lie HTTP/1.1\r\nHost: x\r\nContent-Length: 100\r\n\r\nshort' | nc localhost 8080

サーバは「あと95バイト来るはず」と待ち続け、応答しません。

Content-Length が信用できないと

HTTPリクエストスマグリング

実務のサーバやプロキシが Content-Length と Transfer-Encoding の整合性に神経質なのは、この食い違いが攻撃になるためです。

前段プロキシ「このリクエストは Content-Length どおり10バイトだ」 後段サーバ 「いや Transfer-Encoding があるからこっちが正だ」 ↓ 解釈のズレた残りバイトが「次のリクエスト」として扱われ、 他人のリクエストに攻撃者のデータが混ざる

長さが事前にわからない場合

HTTP/1.1 200 OK
Transfer-Encoding: chunked

7\r\n
Mozilla\r\n      ← 7バイト
9\r\n
Developer\r\n    ← 9バイト
0\r\n            ← 0 で終わり
\r\n

「長さを先に言えないなら、小分けにして毎回長さを言う」という発想です。 この教材では扱いませんが、存在は覚えておいてください。

まとめ

終わりの判定方法
ヘッダー\r\n\r\n を探す
ボディ（長さがわかる）Content-Length の数だけ数える
ボディ（長さが不明）Transfer-Encoding: chunked
HTTP/1.0 の応答接続が閉じられるまで（だから keep-alive が使えなかった）
クイズ: Content-Length を実際より小さく宣言したら？

余ったバイトはバッファに残り、 次のリクエストの先頭として解釈されます。 step05 で「読み切った分をバッファから捨てて、残りを次として読む」ループを書くと、 これが実際に起きるのを確かめられます。

クイズ: GETリクエストにボディを付けられますか？

仕様上は禁止されていませんが、 意味が定義されていないため実質的に使えません。 プロキシが捨てることもあります。データを送るなら POST か PUT を使ってください。

読み切った分をバッファから捨ててループさせると、 1本の接続で複数リクエストを処理できます（keep-alive）。 そこで作る「HTTPコア」を step06 以降ずっと使い回します。
