step17: Access-Control-Expose-Headers

CORSが制限しているのはボディだけではありません。

const r = await fetch('http://api.example/items');
console.log(r.headers.get('X-Total-Count'));  // → null
サーバはちゃんと返しています

DevTools の Network タブにも表示されています。それでも null。
DevToolsに見えている＝JSから読める、ではありません。 DevToolsはブラウザの内部を見ているだけで、JSに渡されるものとは別です。

手を動かす

cd steps/step17-expose-headers
node server.js
ボタンエンドポイントExpose-Headers読めるヘッダー
①クロス /api/hidden無し Cache-Control, Content-Type のみ
②クロス /api/exposedX-Total-Count, X-Request-Id 上記 + 指定した2つ
③クロス /api/exposed-all*全部
④同一 /api/same-origin無し全部

② で X-Rate-Limit-Remaining だけ読めないことに注目してください。列挙していないからです。

④ が重要

同一オリジンなら何も指定しなくても全部読めます。 この制限はクロスオリジンのときだけのものです。

指定しなくても読める7つ

「CORSセーフリスト済みレスポンスヘッダー」と呼ばれます。

  • Cache-Control
  • Content-Language
  • Content-Length
  • Content-Type
  • Expires
  • Last-Modified
  • Pragma

これ以外はすべて、サーバが明示的に公開しない限り読めません。

Access-Control-Expose-Headers: X-Total-Count, Location, Content-Disposition

実務でつまずく場面

返しているもの症状
X-Total-Count（総件数）ページネーションの総ページ数が計算できない
X-RateLimit-Remaining残り回数が表示できない
Location（作成したリソースのURL）201 Created の後どこに移動すればいいかわからない
Content-Disposition（ファイル名）ダウンロードファイル名が取れない

いずれも「サーバは返しているのにフロントで null」という形で現れます。 サーバのログにもDevToolsにもヘッダーが見えているので、原因に気づきにくいのが厄介です。

* の注意点

Access-Control-Expose-Headers: * は credentials: 'include' のリクエストでは無効になり、 「* という名前のヘッダー」を探す扱いになります。
同じ制限が Access-Control-Allow-Headers: * や Access-Control-Allow-Methods: * にもあります。 credentials を使うなら必ず個別に列挙してください。

curlでの確認

curl -i http://localhost:8081/api/hidden
HTTP/1.1 200 OK
X-Total-Count: 1234
X-Request-Id: req-1
X-Rate-Limit-Remaining: 42

普通に見えます。サーバは常に送っています。ブラウザがJSに渡さないだけです。

step12 と同じ構図

CORSはブラウザの中だけの仕組み—— ボディでも、ヘッダーでも、まったく同じです。

クイズ: Content-Type が指定なしで読めるのはなぜ？

CORSセーフリストに入っているからです。 <img> や <script> の時代から ブラウザが必要としてきた基本的な情報であり、 これを隠しても得られるプライバシー上の利益がほとんどないためです。

クイズ: 同一オリジンのリクエストで Expose-Headers は必要？

不要です。 同一オリジンなら全ヘッダーが読めます。 「ローカルでは動いたのに本番で動かない」の典型的な原因になります （開発中はプロキシ経由で同一オリジンだった、など）。
