step14: プリフライト

送る前に許可を尋ねる。step09 で作った OPTIONS を、今度はブラウザが自動で送ります。

このステップでわかること
  • プリフライトが通らなければ、本番リクエストは送られない
  • Access-Control-Request-* に Access-Control-Allow-* で答える
  • プリフライト＝入場許可、本番のACAO＝閲覧許可。両方必要

やりとりの全体像

（ブラウザが「これは単純リクエストではない」と判断する）

→ OPTIONS /api/ok HTTP/1.1
   Origin: http://localhost:8080
   Access-Control-Request-Method: PUT            ← これから使いたいメソッド
   Access-Control-Request-Headers: content-type  ← これから付けたいヘッダー

← HTTP/1.1 204 No Content
   Access-Control-Allow-Origin: *
   Access-Control-Allow-Methods: GET, POST, PUT, DELETE, OPTIONS
   Access-Control-Allow-Headers: Content-Type, X-Demo

（ここで初めて本番が送られる）

→ PUT /api/ok HTTP/1.1
   Origin: http://localhost:8080
   Content-Type: application/json

← HTTP/1.1 200 OK
   Access-Control-Allow-Origin: *      ← 本番にも必要！

「送ってみてダメだった」ではなく「送る前に諦める」のがプリフライトです。

実装

// プリフライトかどうかの見分け方
if (req.method === "OPTIONS" && req.headers["access-control-request-method"]) {

  const wantMethod  = req.headers["access-control-request-method"];
  const wantHeaders = req.headers["access-control-request-headers"];

  return res.send(204, {
    "Access-Control-Allow-Origin":  "*",
    "Access-Control-Allow-Methods": "GET, POST, PUT, DELETE, OPTIONS",
    "Access-Control-Allow-Headers": "Content-Type, X-Demo",
  });
}
OPTIONS が来ただけではプリフライトとは限らない

step09 のような普通の OPTIONS もあります。 Access-Control-Request-Method の有無で判定してください。

プリフライトの応答は 2xx である必要がある

204 No Content が最も自然です（ボディは不要なので）。 401 や 404 を返すとプリフライトは失敗します。
認証ミドルウェアが OPTIONS にも認証を要求してしまい壊れる—— 実務でよくある事故です。プリフライトには Authorization ヘッダーは付きません。

手を動かす

cd steps/step14-preflight
node server.js

プリフライトが飛ぶとコンソールに ★ が出ます。

パスプリフライト応答本番応答のACAO
/api/ok正しく返すあり
/api/strict返さない（404）あり
/api/preflight-only正しく返す無し

成功する例

① POST+JSON　② PUT　③ DELETE　④ GET + 独自ヘッダー X-Demo

④ に注目 — GETでもプリフライトが飛ぶ

独自ヘッダーを1つ付けただけで「単純リクエスト」の条件を外れます。 Authorization: Bearer ... を付けるAPIがプリフライトを避けられないのはこれが理由です。

失敗する3パターン

⑤ プリフライトに応答しないAPI

コンソールを見ると、OPTIONS は届いているが POST は届いていません。 ブラウザは許可が取れなかったので、本番を送るのをやめました。

⑥ 許可されていないヘッダー

X-Secret を付けると、プリフライトの段階で失敗します。 サーバは Access-Control-Allow-Headers: Content-Type, X-Demo としか答えないためです。

実務で Authorization や X-Requested-With を追加したときに 突然壊れるのは、たいていこれです。

⑦ プリフライトは通るが本番にACAOが無い

一番わかりにくいパターン
  • ★ プリフライトが通っている
  • 本番の PUT も届いている（サーバは200を返している）
  • それでもJSは読めない

プリフライトは「入場許可」、本番のACAOは「閲覧許可」。両方必要です。
OPTIONS のときだけCORS設定を書いて、本番のレスポンスに付け忘れる—— 実務で非常に多いミスです。

curlでプリフライトを手動再現する

curl -i -X OPTIONS \
  -H 'Origin: http://localhost:8080' \
  -H 'Access-Control-Request-Method: PUT' \
  -H 'Access-Control-Request-Headers: content-type' \
  http://localhost:8081/api/ok
HTTP/1.1 204 No Content
Access-Control-Allow-Origin: *
Access-Control-Allow-Methods: GET, POST, PUT, DELETE, OPTIONS
Access-Control-Allow-Headers: Content-Type, X-Demo
ブラウザがやっていることは、これだけです

魔法ではありません。 CORSがうまくいかないときは、この curl を打って サーバが何を返しているかを直接確かめるのが最短です。

プリフライトが飛ぶ条件（まとめ）

やることプリフライト
GET / HEAD飛ばない
POST + text/plain / x-www-form-urlencoded / multipart/form-data飛ばない
POST + application/json飛ぶ
PUT / DELETE / PATCH飛ぶ
独自ヘッダーを付ける（メソッド問わず）飛ぶ
クイズ: プリフライトが失敗したら、本番リクエストはサーバに届きますか？

届きません。 step12 では「fetchが失敗してもリクエストは届いていた」と学びましたが、 プリフライトが失敗する場合だけは本番が送られません。この違いは重要です。

クイズ: プリフライトのレスポンスにだけCORSヘッダーを書くと、なぜ動かない？

プリフライトは「送ってよいか」の確認にすぎません。 本番の応答を読んでよいかは、本番の応答に付いた Access-Control-Allow-Origin で改めて判定されます。
