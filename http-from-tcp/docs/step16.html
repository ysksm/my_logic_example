step16: credentials とクロスオリジンの Cookie

第4章の山場。Cookie・プリフライト・ACAO がここで全部つながります。

このステップでわかること
  • fetch は既定でクロスオリジンにCookieを送らない
  • credentials 付きのとき Access-Control-Allow-Origin: * は使えない
  • Vary: Origin が必要な理由
  • 「オリジン」と「サイト」は別物（発展）

fetch は既定でCookieを送らない

credentials意味
'omit'絶対に送らない
'same-origin'（既定）同一オリジンのときだけ送る
'include'クロスオリジンでも送る。サーバ側の許可が必要

XMLHttpRequest の withCredentials = true が同じ役割です。

Set-Cookie を受け入れるのにも 'include' が必要

省くと、サーバが Set-Cookie を返しても ブラウザは保存しません。「ログインAPIは200を返すのにログインできない」の原因になります。

実験1・2 — Cookieが送られるかを比べる

cd steps/step16-credentials
node server.js

①指定なしログイン中: falseCookie ヘッダー : 届いていません
②'include'ログイン中: trueCookie ヘッダー : sid=...
① は通信自体は成功しています

ステータスは 200。ただCookieが送られていないので、 サーバから見れば未ログインの他人です。
「APIは動いているのにログイン状態にならない」という症状の正体がこれです。

実験3 — サーバ側の設定ミス2種

③ Access-Control-Allow-Origin: * ＋ credentials: 'include'

The value of the 'Access-Control-Allow-Origin' header in the response must not
be the wildcard '*' when the request's credentials mode is 'include'.
なぜ禁止されているのか

* は「誰でもどうぞ」という意味です。 そこにユーザーのCookie（＝本人の権限）が乗ると、 どんなサイトからでも、そのユーザーとしてAPIを叩いて結果を読めることになります。
「誰でも」と「本人の権限」は同時に成立させてはいけない。だからブラウザが拒否します。

④ Allow-Credentials の付け忘れ

The value of the 'Access-Control-Allow-Credentials' header in the response is ''
which must be 'true' when the request's credentials mode is 'include'.

Origin の一致だけでは足りません。 「Cookieを伴ってよい」という明示的な許可が別途必要です。

正しい実装

function corsWithCredentials(origin) {
  if (!ALLOWED_ORIGINS.has(origin)) return { "Vary": "Origin" };
  return {
    "Access-Control-Allow-Origin": origin,        // ← "*" ではなく実際の値
    "Access-Control-Allow-Credentials": "true",   // ← これが無いと通らない
    "Vary": "Origin",                             // ← キャッシュ事故を防ぐ
  };
}
  1. Access-Control-Allow-Origin に * は使えない。Origin をそのまま返す
  2. Access-Control-Allow-Credentials: true を返す
  3. プリフライトが飛ぶ場合は、プリフライトの応答にもこの2つが必要
  4. Vary: Origin を付ける
Vary: Origin はなぜ必要か
CDN / プロキシ ↓ A社向けの応答（ACAO: https://a.example）をキャッシュ ↓ それをB社に配ってしまう → B社からは読めない（あるいはその逆の事故）

許可した場合も、許可しなかった場合も、必ず付けてください。

発展（任意）: オリジンとサイトは別物

ここまでの実験では SameSite=Lax のままCookieが送られていました。不思議ではありませんか？

概念判定に使うもの
オリジンスキーム + ホスト + ポート
サイトスキーム + 登録可能ドメイン（eTLD+1）。ポートは無関係
http://localhost:8080 と http://localhost:8081 → 別オリジン（ポートが違う）だが、同じサイト（ホストが同じ） http://localhost:8080 と http://127.0.0.1:8081 → 別オリジン かつ 別サイト（ホスト名が違う）

SameSite 属性が見ているのは「オリジン」ではなく「サイト」です。 だからポートが違うだけの今回のケースは same-site であり、Lax でもCookieが送られます。

発展の実験（⑤⑥⑦）

http://127.0.0.1:8081 にすると別サイトになります。 同じAPIサーバに別の名前でアクセスするだけです。

  1. ⑤ 127.0.0.1 側に SameSite=Lax でログイン → 応答は成功するが、Cookieは保存されない
  2. ⑥ 127.0.0.1 側の /api/me → Cookieが届かない
  3. ⑦ SameSite=None; Secure でログインし直す → 保存される
  4. ⑥ をもう一度 → Cookieが届く

DevTools → Application → Cookies → http://127.0.0.1:8081 で確認してください。

Secure なのに http で動く理由

step11 で見たとおり、ブラウザは localhost / 127.0.0.1 を例外的に「安全なオリジン」として扱います。本番では本物のHTTPSが必要です。

うまくいかない場合

ブラウザのサードパーティCookieブロックを確認してください。 Chrome: 設定 → プライバシーとセキュリティ → サードパーティCookie。 Safari は既定でブロックするため、この発展実験は動きません。

クロスサイトでCookieを使うための条件

層必要なもの
CookieSameSite=None; Secure
fetchcredentials: 'include'
CORS（本番）Access-Control-Allow-Origin: <実際のOrigin> ＋ Allow-Credentials: true
CORS（プリフライト）同上
キャッシュVary: Origin
5層すべてが揃わないと動きません

1つでも欠けると失敗します。 「クロスオリジンのCookieがつらい」と言われるのはこのためです。
step19 では、この全部を不要にする方法を扱います。

クイズ: http://a.example:8080 と http://a.example:9000 は？

別オリジン、同じサイトです。
→ CORSの対象にはなる（ACAOが必要）が、SameSite の制限は受けません。
