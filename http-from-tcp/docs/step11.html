step11: Cookie 属性とセッション

属性でCookieの振る舞いを制御する。SameSite は第4章の重要な前提です。

このステップでわかること
  • Path / Max-Age / HttpOnly / Secure / SameSite の役割
  • localhost は例外的に「安全なオリジン」として扱われる
  • セッションID方式 —— Cookieには「鍵」だけを入れる

属性の一覧

Set-Cookie: sid=abc123; Path=/; Max-Age=3600; HttpOnly; Secure; SameSite=Lax
            └───┬───┘  └────────────────────┬───────────────────────────┘
             名前=値                       属性（; 区切り）
属性意味付けないと
Path=/fooそのパス以下にだけ送るサイト全体に送られる
Domain=example.comサブドメインにも送るそのホストにだけ送る（より安全）
Max-Age=36003600秒で消えるブラウザを閉じると消える
HttpOnlyJavaScriptから読めないdocument.cookie で読める＝XSSで盗まれる
SecureHTTPSのときだけ送るhttpでも送られる＝盗聴される
SameSite他サイト起点のリクエストに付けるか既定は Lax

手を動かす（ブラウザ必須）

cd steps/step11-cookie-attributes
node server.js

http://localhost:8080/ を開き、 「属性つきCookieを5個受け取る」を押してください。

① HttpOnly

ページに2つの表示が並びます。

  • サーバが受け取ったCookie: plain secret temp …
  • document.cookie: secret が無い

ログインすると sid も同様です。 HttpOnly は「JavaScriptから隠す」だけの属性で、通信には普通に載ります。

② Path

/ と /admin を行き来してください。 area は /admin でだけ表に現れます。

③ Max-Age

temp は10秒後にリロードすると消えます。

④ Secure と localhost の例外（重要）

onlyhttps=secure-attr; Path=/; Secure は http なのに保存されています。

これは仕様どおり

ブラウザは localhost と 127.0.0.1 を 「潜在的に信頼できるオリジン（potentially trustworthy origin）」 として扱い、httpでも安全なオリジンとみなします。

本物のドメインを http で使った場合、Secure 付きCookieは保存されません。

step16 で効いてきます

クロスサイトでCookieを送るには SameSite=None; Secure が必要ですが、 localhost ならHTTPSを用意しなくても実験できます。

⑤ SameSite（step16の予告）

値他サイトからのリクエストにCookieを付けるか
Strict一切付けない（他サイトのリンクから来ると未ログイン扱い）
Lax（既定）トップレベルのGET遷移（リンククリック）だけ付ける
None常に付ける。ただし Secure が必須
Lax が既定になった理由 — CSRF対策
攻撃者のページ <form method="POST" action="https://bank.example/transfer"> （自動送信） ↓ リクエストは届く（step12でやるとおり、フォーム送信は止められない） ↓ しかし SameSite=Lax なら Cookie が付かない → 認証が通らない

CORSとCSRFは別物です。 step18 で改めて整理します。

セッションID方式

const sid = randomUUID();                       // 推測できないID
sessions.set(sid, { user, loginAt });           // 中身はサーバが持つ

"Set-Cookie": `sid=${sid}; Path=/; HttpOnly; SameSite=Lax`
ブラウザ サーバ ┌──────────┐ ┌──────────────────────┐ │ sid=abc… │ ←──鍵だけ── │ abc… → { user: 山田 } │ └──────────┘ │ def… → { user: 佐藤 } │ └──────────────────────┘ 書き換えても 対応表はサーバが持つので 存在しないIDになるだけ なりすませない
なぜ中身を入れないのか

step10 の実験4で見たとおり、Cookieの値は書き換えられます。 Cookie: user=admin のように中身そのものを入れると、書き換えられて終わりです。

ログアウト時の注意

サーバ側の sessions からも消してください。 Cookieを消しただけでは、盗まれたIDがまだ有効なままです。

クイズ: HttpOnly を付けると通信は暗号化されますか？

されません。HttpOnly はJavaScriptから隠すだけです。 通信を暗号化するのはHTTPS（TLS）の役割で、Cookie側では Secure 属性が 「暗号化された経路でだけ送る」ことを保証します。役割が別なので両方付けます。
