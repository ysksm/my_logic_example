step09: DELETE と適切な応答

第2章の締めくくり。そしてここで OPTIONS が初登場します。

このステップでわかること
  • DELETEが2回目も成功を返す理由
  • 405 には Allow ヘッダーが必須
  • OPTIONS = 「このURLで何ができるのか」を尋ねるメソッド
step14 への伏線

ここで手で実装する OPTIONS を、 第4章ではブラウザが勝手に送ってきます。それがプリフライトです。

DELETEは2回目も 204

curl -i -X DELETE http://localhost:8080/items/1   # → 204 No Content
curl -i -X DELETE http://localhost:8080/items/1   # → 204 No Content

「もう無いのだから404では？」と思うかもしれません。

DELETEの目的は「そのURLに何も無い状態にすること」

2回目もその状態は達成されているので、成功を返すのが自然です。 これによりDELETEは冪等になり、クライアントは安心して再送できます。

404を返す設計もありえますが、その場合クライアントは 「本当に無かったのか、自分の再送が成功した後なのか」を区別できません。

204 にはボディも Content-Length も無い

HTTP/1.1 204 No Content
Connection: keep-alive

405 には Allow を付ける

curl -i -X PATCH http://localhost:8080/items/1
HTTP/1.1 405 Method Not Allowed
Allow: GET, PUT, DELETE, OPTIONS

Allow は405のとき必須です（RFC 9110）。 「ダメです」だけでなく「これならできます」を返すのがHTTPの作法です。

404 と 405 の違い
  • 404 … URLが存在しない
  • 405 … URLはあるが、そのメソッドは使えない
const ALLOWED = {
  collection: ["GET", "POST", "OPTIONS"],
  item:       ["GET", "PUT", "DELETE", "OPTIONS"],
};

return res.json(405, { error: "Method Not Allowed" },
                { "Allow": ALLOWED.item.join(", ") });

OPTIONS — 何ができるかを尋ねる

curl -i -X OPTIONS http://localhost:8080/items/1
HTTP/1.1 204 No Content
Allow: GET, PUT, DELETE, OPTIONS
curl -i -X OPTIONS http://localhost:8080/items
HTTP/1.1 204 No Content
Allow: GET, POST, OPTIONS
OPTIONS は「実際に何かをする」メソッドではない

そのURLに対して何ができるのかを尋ねるだけ。 安全（状態を変えない）で冪等です。

これがCORSのプリフライトの正体です

step14 でブラウザが勝手に OPTIONS を送る場面に出会います。 そのとき「あの『何ができるか尋ねるメソッド』か」と思い出してください。
ただしCORSのプリフライトは Allow ではなく Access-Control-Allow-Methods という別のヘッダーで答えます。
