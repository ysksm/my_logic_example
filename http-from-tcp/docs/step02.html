step02: リクエストラインを読む

1行目を分解し、応答を手書きする。ここで初めてHTTPサーバになります。

このステップでわかること
  • リクエストラインは「メソッド・ターゲット・バージョン」の3要素
  • 応答も同じ形。1行目は「ステータスライン」
  • \r\n\r\n（空行）がヘッダーの終わりの唯一の目印
step01からの差分
  • 受信テキストの1行目だけを空白で3分割する
  • HTTPの応答テキストを手書きして返す

2つの「1行目」

リクエストライン（クライアント → サーバ）

GET /hello?a=1 HTTP/1.1
└┬┘ └────┬───┘ └──┬───┘
 │        │        └── HTTPバージョン
 │        └────────── リクエストターゲット（パス＋クエリ）
 └─────────────────  メソッド

ステータスライン（サーバ → クライアント）

HTTP/1.1 200 OK
└──┬───┘ └┬┘ └┬┘
   │      │   └── 理由句（人間向け。ブラウザは見ない）
   │      └────── ステータスコード（機械が見るのはこれ）
   └───────────── HTTPバージョン
どちらも「半角スペース区切りの3要素」

だから line.split(" ") で分解できます。 HTTPがテキストプロトコルであることの分かりやすい例です。

メッセージ全体の形

┌─────────────────────────────┐ │ GET /hello HTTP/1.1 \r\n │ ← 1行目（リクエストライン） ├─────────────────────────────┤ │ Host: localhost:8080 \r\n │ │ User-Agent: curl/8.7.1 \r\n │ ← ヘッダー（0行以上） │ Accept: */* \r\n │ ├─────────────────────────────┤ │ \r\n │ ← 空行！ここでヘッダーが終わる ├─────────────────────────────┤ │ （ボディ。GETでは普通は無い） │ └─────────────────────────────┘
応答も完全に同じ構造
HTTP/1.1 200 OK\r\n
Content-Type: text/plain; charset=utf-8\r\n
Content-Length: 42\r\n
Connection: close\r\n
\r\n            ← この空行がヘッダーの終わり
（ここからボディ）

手を動かす

cd steps/step02-request-line

実験1: 初めてのHTTP応答

curl -v http://localhost:8080/hello

ブラウザ http://localhost:8080/ でも文字が表示されます。

実験2: メソッドは自由に名乗れる

curl -v -X POST   http://localhost:8080/anything
curl -v -X DELETE http://localhost:8080/users/1
curl -v -X BANANA http://localhost:8080/

BANANA すら通ります。メソッドはただの文字列で、 意味を与えるのはサーバ側の実装です。

実験3（重要）: 空行を消すとどうなるか

responseHead の最後の "\r\n" を消して再起動し、 curl -v してみてください。

* Empty reply from server

あるいは curl がずっと待ち続けます。 クライアントは「ヘッダーがまだ続く」と思って待っているのです。 確認したら元に戻してください。

実験4: 手で1リクエスト打つ

printf 'GET /manual HTTP/1.1\r\nHost: localhost\r\n\r\n' | nc localhost 8080

これが「HTTPを喋る」ということです。

まとめ

今日の要点
  • リクエストもレスポンスも「1行目＋ヘッダー＋空行＋ボディ」
  • 行区切りは \r\n、ヘッダーの終わりは \r\n\r\n
  • メソッドはただの文字列。サーバが意味を決める
  • Content-Length はバイト数（文字数ではない）
クイズ: Content-Length を実際のボディ長より大きくしたら？

クライアントは「まだ続きがある」と思って待ち続けます。 curl はタイムアウトするか、接続が閉じられた時点で transfer closed with N bytes remaining to read のようなエラーを出します。 実際に試してみてください。

クイズ: なぜこのステップでは Connection: close を付けたのか？

まだ「1接続で複数リクエスト」を処理できないからです。 HTTP/1.1 は既定で接続を使い回す（keep-alive）ので、 閉じるつもりなら明示的に宣言する必要があります。step05 で対応します。
