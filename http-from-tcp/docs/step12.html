step12: 同一オリジンポリシー

第4章のはじまり。ここが目的地です。まず「CORSとは誰の仕組みか」を確定させます。

このステップの核心

fetch が失敗しても、サーバにはリクエストが届き、200 OK が返っています。
CORSはサーバの機能ではなく、ブラウザの機能です。

2つのサーバを1プロセスで動かします

オリジンA http://localhost:8080 … 実験ページを配る（ブラウザが表示する側） オリジンB http://localhost:8081 … API（別オリジン）

step11からの差分は、HTTPコアに「どちらのサーバのログか」を示す label を足しただけです。

オリジンとは

http://localhost:8080 └─┬─┘ └───┬───┘ └┬─┘ スキーム ホスト ポート この3つがすべて一致するときだけ「同一オリジン」
比較対象（基準: http://localhost:8080）判定理由
http://localhost:8080/other/path同一パスは関係ない
http://localhost:8081別ポートが違う
https://localhost:8080別スキームが違う
http://127.0.0.1:8080別ホスト名が違う（同じマシンでも）
http://sub.localhost:8080別ホスト名が違う
step16 への伏線

「オリジン」と「サイト」は別の概念です。 サイトの判定にポートは関係しません。step16 でこの差が効いてきます。

手を動かす

cd steps/step12-same-origin
node server.js

ブラウザで http://localhost:8080/ を開いてください。
必ずサーバのコンソールも見えるようにしておいてください。

実験1: 同一オリジン → 成功

「① GET /api/same-origin」。8080 自身が返しているので何の制限もありません。

実験2: 別オリジン → 失敗（このステップの核心）

「② GET http://localhost:8081/api/hello」を押すと失敗します。
そのあと必ずサーバのコンソールを見てください。

[API 8081] GET /api/hello  Origin: http://localhost:8080
リクエストは届いている
  • サーバは何も拒否していない
  • 通信は完全に成功している（200 OK を返している）
  • それでも JavaScript は中身を読めない

ブラウザは何と言っているか

DevTools の Console:

Access to fetch at 'http://localhost:8081/api/hello' from origin
'http://localhost:8080' has been blocked by CORS policy:
No 'Access-Control-Allow-Origin' header is present on the requested resource.

「has been blocked by CORS policy」— 誰にブロックされたのか。ブラウザにです。

実験3: curlなら成功する

curl -s http://localhost:8081/api/hello

普通に読めます。

CORSはアクセス制御ではない

curl にも、サーバ間通信にも、 Pythonのスクリプトにも、CORSは一切効きません。 効くのは「ブラウザの中で動くJavaScript」に対してだけです。

実験4: <img> なら読み込める

「③ <img src="http://localhost:8081/api/pixel">」を押すと成功します。

止めているのは「送ること」ではなく「読むこと」
  • <img> で他オリジンの画像を表示する → できる
  • その画像を <canvas> に描いて getImageData() する → 止められる
  • <script src> で他オリジンのJSを実行する → できる
  • <form> で他オリジンにPOSTする → できる（← CSRFが成立する理由）

<img> や <script> はCORSが生まれるずっと前から 他オリジンを読み込めていました。今もそのままです。

何のための仕組みなのか

あなたが銀行にログインしているとします。攻撃者のページを開いたとき、 そのページのJSがこう書けたらどうなるでしょう。

const r = await fetch('https://bank.example/api/balance', {
  credentials: 'include'      // ブラウザがあなたのCookieを自動で付ける
});
const data = await r.json();  // 残高が読めてしまう
sendToAttacker(data);
CORSが守っているのはサーバではなく、利用者（あなた）です

だからブラウザは「別オリジンの応答をJSに渡さない」という規則を持っています。 そのうえで「このオリジンになら読ませてよい」とサーバが宣言する手段が、 次のステップの Access-Control-Allow-Origin です。

クイズ: fetch が失敗したとき、サーバにリクエストは届いていましたか？

届いています。 （プリフライトが飛ぶ場合だけは、本番リクエストが送られないことがあります。step14で扱います）
だから「CORSエラーだから何も起きていない」と考えるのは間違いです。 副作用のあるリクエストなら、副作用はもう発生しています。

クイズ: <form> での他オリジンPOSTはCORSで止められますか？

止められません。 これがCSRFが成立する理由であり、CORSがCSRF対策にならない理由です（step18で詳述）。
