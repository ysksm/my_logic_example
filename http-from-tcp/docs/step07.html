step07: POST

ボディはただのバイト列。それが何なのかを教えるのが Content-Type です。

このステップでわかること
  • Content-Type でボディの読み方を切り替える
  • フォーム形式とクエリ文字列は書式が同じ
  • 415 Unsupported Media Type の使いどころ

GET と POST の違い

GET

GET /search?name=%E5%B1%B1%E7%94%B0&age=20 HTTP/1.1
Host: localhost:8080

POST

POST /submit HTTP/1.1
Host: localhost:8080
Content-Type: application/x-www-form-urlencoded
Content-Length: 41

name=%E5%B1%B1%E7%94%B0&age=20
GETPOST
データの場所URL（リクエストライン）ボディ
アドレスバー?name=… が付く/submit のまま
履歴・ログ残る残らない
書式同じ（name=value&…）

書式が同じなので、parseUrlEncoded() はクエリにもボディにも使い回せます。

Content-Type がすべてを決める

Content-Typeボディの形誰が使う
application/x-www-form-urlencodedname=taro&age=20HTMLフォーム（既定）
application/json{"name":"taro"}fetch / APIクライアント
text/plainただの文字列単純な用途
multipart/form-data境界文字列で区切るファイルアップロード
// "application/json; charset=utf-8" のようにパラメータが付くので
// ";" より前だけを見る
const contentType = (req.headers["content-type"] ?? "")
  .split(";")[0].trim().toLowerCase();

if (contentType === "application/x-www-form-urlencoded")
  return parseUrlEncoded(raw);

if (contentType === "application/json")
  return JSON.parse(raw);

return { unsupported: true };   // → 415
この3つを覚えておいてください

x-www-form-urlencoded / multipart/form-data / text/plain —— step13 の「単純リクエスト」の条件でそのまま再登場します。 application/json が入っていないことが、CORSの挙動を分けます。

手を動かす

cd steps/step07-post
node server.js

ブラウザで http://localhost:8080/ を開いてください。

実験1: HTMLフォームのPOST

1つ目のフォームを送信し、サーバのコンソールで生の通信を見てください。 アドレスバーは /submit のままです。

実験2: JSONのPOST

curl -v -H 'Content-Type: application/json' \
     -d '{"name":"太郎","tags":["a","b"]}' http://localhost:8080/submit

実験3: 415 Unsupported Media Type

curl -v -H 'Content-Type: application/xml' -d '<a/>' http://localhost:8080/submit

415 は「文法は正しいが、この形式は受け付けない」。 400（そもそも壊れている）とは別物です。

実験4: Content-Typeを詐称する

curl -H 'Content-Type: application/json' -d 'name=taro' http://localhost:8080/submit

400 が返ります。Content-Type は宣言にすぎず、 中身とは無関係です。サーバは必ず「宣言どおりでなかった場合」を処理する必要があります。

まとめ

今日の要点
  • ボディはバイト列。意味を与えるのは Content-Type
  • Content-Type はパラメータ付きで来る → ; より前を見る
  • 宣言は信用できない → パース失敗を必ず処理する
  • 400（壊れている） と 415（形式が非対応）を使い分ける
クイズ: HTMLの <form> は application/json で送れますか？

送れません。 <form enctype> に指定できるのは application/x-www-form-urlencoded、multipart/form-data、 text/plain の3つだけです。
…この3つ、どこかで見ませんでしたか？ step13 の「単純リクエスト」の条件と同じです。 偶然ではありません。

クイズ: Content-Type が無いPOSTが来たら？

仕様上は application/octet-stream （ただのバイト列）とみなしてよいことになっています。 実務では 400 か 415 を返して明示的に拒否するのが安全です。
