step19（特別演習）
同一オリジン化リバースプロキシ

CORSを「設定する」のではなく「発生させない」もうひとつの解。

ブラウザ ──→ http://localhost:8080 ページ＋プロキシ（＝唯一のオリジン） │ /api/* だけを転送 ↓ http://127.0.0.1:9001 バックエンドAPI（CORS設定は一切なし）
ブラウザから見えるオリジンは1つだけ

だから同一オリジンポリシーの対象にならず、 CORSは最初から発生しません。

サーバが初めてTCPクライアントになる

const upstream = net.createConnection({ host, port }, () => {
  upstream.write(upstreamRequest);   // step02 で手書きしたのと同じ形のテキスト
});

let received = Buffer.alloc(0);
upstream.on("data", (chunk) => { received = Buffer.concat([received, chunk]); });
upstream.on("end",  () => { /* 応答を分解してブラウザへ返す */ });
net.createServer の逆が net.createConnection

書き込むのは メソッド パス HTTP/1.1\r\n... というテキスト。 第1章でやったことがそのまま使えます。

1リクエストにつき4つのダンプ

▼ ブラウザ → プロキシ ▶ プロキシ → バックエンド ← Host が書き換わっている ◀ バックエンド → プロキシ ▲ プロキシ → ブラウザ

手を動かす

cd steps/step19-reverse-proxy
node server.js

実験1: 直接 vs プロキシ経由

ボタン呼び先結果
①http://localhost:9001/api/hello（直接）失敗
②/api/hello（プロキシ経由）成功

バックエンドは同じです。CORSヘッダーを1つも返していません。 違うのは「ブラウザから見て何オリジンか」だけ。

実験2: プリフライトが飛ばない

③ PUT /api/items/1 + JSON　④ DELETE /api/items/1

step14 なら確実にプリフライトが飛んだ組み合わせです。 サーバのコンソールに OPTIONS が1つも出ないことを確認してください。 往復が1回減ります。

実験3: Cookieが素直に動く

⑤ POST /api/login　⑥ GET /api/me → ログイン中: true

credentials: 'include' を一度も書いていません。 Cookieの属性も Path=/; HttpOnly; SameSite=Lax とごく普通です。

Cookieはどこのものになるか

バックエンドが発行: Set-Cookie: sid=...; Path=/; HttpOnly; SameSite=Lax ↓ プロキシがそのまま転送 ブラウザから見ると: 「http://localhost:8080 が返した Set-Cookie」 ↓ localhost:8080 のファーストパーティCookieとして保存される

DevTools → Application → Cookies を見ると、Cookieは http://localhost:8080 のものとして保存されています。 バックエンドが発行したのに、です。

step16 で必要だった5層がすべて不要になる

SameSite=None も Secure も credentials:'include' も Allow-Credentials も Vary: Origin も——1つも要りません。

2つの解の比較

CORSを設定する（step13〜18）プロキシで同一オリジンにする（step19）
ブラウザから見たオリジン2つ1つ
プリフライト条件次第で飛ぶ（往復1回分の遅延）飛ばない
CookieSameSite=None; Secure ＋ credentials:'include' ＋ Allow-Credentials ファーストパーティCookieとして普通に動く
APIの改修必要不要
運用サーバは1つでよいプロキシ層が増える。障害点も増える
通信量ブラウザ→API 直通すべてプロキシを経由する
向いている場面不特定多数に公開するAPI、
別会社のフロントから叩かれるAPI		 自社フロント＋自社API、
APIを改修できない場合
実務で見かけるものは、ほぼこの2つのどちらか
  • Vite の server.proxy / Next.js の rewrites → step19 の方式
  • Nginx の location /api/ { proxy_pass ...; } → step19 の方式
  • Kubernetes Ingress のパスベースルーティング → step19 の方式
  • 公開REST API の Access-Control-Allow-Origin: * → step13 の方式

プロキシ実装の要点

1. ホップバイホップヘッダーを転送しない

const HOP_BY_HOP = new Set([
  "connection", "keep-alive", "proxy-authenticate", "proxy-authorization",
  "te", "trailer", "transfer-encoding", "upgrade",
]);

これらは「この1本の接続についての取り決め」です。 次の接続にそのまま持ち越すと壊れます。

2. Host を書き換え、元の情報は X-Forwarded-* で渡す

outHeaders.push(`Host: ${BACKEND_HOST}:${BACKEND_PORT}`);
outHeaders.push(`X-Forwarded-Host: ${req.headers["host"]}`);
outHeaders.push(`X-Forwarded-Proto: http`);
outHeaders.push(`X-Forwarded-For: 127.0.0.1`);

3. 同名ヘッダーを潰さない

if (headers.has(key)) headers.get(key).values.push(value);

Set-Cookie が2行あるとき片方を捨てるとログインが壊れます。 step10 の「Set-Cookie は連結してはいけない」がここで効きます。

4. Content-Length は自分で計算し直す

注意点

転送先を固定する

URLの一部を転送先ホストにするような作りにすると、 社内ネットワークへの踏み台（SSRF）になります。 /proxy?url=http://169.254.169.254/ のような設計は絶対に避けてください。

  • クライアントが送ってきた X-Forwarded-For を信用しない（偽装できます）
  • この実装は Transfer-Encoding: chunked、WebSocket（Upgrade）、 ストリーミングに対応していません
  • バックエンドへ Connection: close を送っているので毎回TCP接続を張り直しています。 実務のプロキシは接続プールを持ちます
クイズ: なぜプロキシ経由だとプリフライトが飛ばないのですか？

ブラウザから見て同一オリジンだからです。 プリフライトはクロスオリジンリクエストのための仕組みなので、 そもそも判定対象になりません。

クイズ: Connection ヘッダーを転送してはいけないのはなぜ？

「この1本のTCP接続をどう扱うか」の取り決めだからです。 ブラウザ↔プロキシ間の取り決めを、プロキシ↔バックエンド間にそのまま持ち込むと 接続管理が壊れます。

  2. 第2章 — 4つのメソッドと、それぞれに適したステータスコード
  3. 第3章 — Cookieでステートレスなプロトコルに状態を持たせた
  4. 第4章 — CORSの各ヘッダーを1つずつ動かして確かめた
  5. 第5章 — 安全な許可リストと、CORSで防げないもの
  6. 特別演習 — プロキシでオリジンそのものを畳んだ

「なんとなくCORSで落ちた」ではなく、 ブラウザが、どの段階で、どの条件を満たさなかったのか を具体的に切り分けられるはずです。

  • そもそもプリフライトは飛んだか？ 通ったか？
  • 本番の応答に ACAO はあるか？ 値は一致しているか？
  • credentials を使っているのに * を返していないか？
  • 読みたいのはボディか、ヘッダーか（Expose-Headers）？
  • そもそもCORSで解くべきか、プロキシで畳むべきか？
