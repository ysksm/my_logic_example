ここで作る「HTTPコア」を step06 以降ずっと使い回します。第1章の総仕上げです。

  • 1本のTCP接続で複数リクエストを処理する（keep-alive）

  • レスポンス組み立ての部品 res.text() / .html() / .json() / .send()

keep-alive

HTTP/1.0 — 1リクエスト＝1接続

接続 → GET /index.html → 応答 → 切断 接続 → GET /style.css → 応答 → 切断 接続 → GET /logo.png → 応答 → 切断 ← 画像20個なら20回の接続確立

HTTP/1.1 — 既定で使い回す

接続 → GET /index.html → 応答 → GET /style.css → 応答 → GET /logo.png → 応答 → （閉じたい側が Connection: close と宣言）
サーバ実装への影響

バッファに残ったバイトが 「次のリクエスト」かもしれません。だから読み切ったら捨てて、もう一度読む ループが要ります。

ループの中身

socket.on("data", (chunk) => {
  buffer = Buffer.concat([buffer, chunk]);

  while (!closed) {
    const headerEnd = buffer.indexOf("\r\n\r\n");
    if (headerEnd === -1) break;                   // ヘッダーがまだ

    // …ヘッダー解析…

    const bodyStart = headerEnd + 4;
    const contentLength = Number(headers["content-length"] ?? 0);
    if (buffer.length < bodyStart + contentLength) break;   // ボディがまだ

    const body = buffer.subarray(bodyStart, bodyStart + contentLength);

    // ★ 読み切った分を捨てる。残りは次のリクエスト
    buffer = buffer.subarray(bodyStart + contentLength);

    handler(req, res);
  }
});

return ではなく break にすること、 そしてバッファを削ることがポイントです。

レスポンス組み立て

send(status, headers = {}, body = "") {
  const bodyBuf = Buffer.isBuffer(body) ? body : Buffer.from(String(body));
  const noBody = status === 204 || status === 304;

  const out = { ...headers };
  if (!noBody) out["Content-Length"] = String(bodyBuf.length);
  out["Connection"] = keepAlive ? "keep-alive" : "close";

  const lines = [`HTTP/1.1 ${status} ${REASON[status]}`];
  for (const [name, value] of Object.entries(out)) {
    // 配列を渡すと同じ名前の行を複数出す（Set-Cookie 用。step10で使う）
    for (const v of Array.isArray(value) ? value : [value])
      lines.push(`${name}: ${v}`);
  }

  socket.write(Buffer.concat([
    Buffer.from(lines.join("\r\n") + "\r\n\r\n"), bodyBuf
  ]));
}

実験1: 1本の接続で2リクエスト

curl -v http://localhost:8080/plain http://localhost:8080/json

curl 側に * Re-using existing connection、 サーバ側に [この接続の 1 本目] [この接続の 2 本目] が出ます。

実験2（重要）: パイプライン

printf 'GET /plain HTTP/1.1\r\nHost: x\r\n\r\nGET /json HTTP/1.1\r\nHost: x\r\nConnection: close\r\n\r\n' \
  | nc localhost 8080

1回の data イベントで2リクエストが同時に届きます。 それでもループのおかげで両方に応答が返ります。 これが「TCPにはメッセージの境界がない」ことの実感です。

実験3: 204 No Content

curl -v http://localhost:8080/empty
HTTP/1.1 204 No Content
Connection: keep-alive

Content-Length がありません。

第1章のまとめ

step学んだこと

02「1行目＋ヘッダー＋空行＋ボディ」。行区切りは \r\n

051接続で複数リクエスト → 読み切って捨ててループ
これで「HTTPサーバ」が完成しました

クイズ: 204 に Content-Length: 0 を付けてはいけないのはなぜ？

仕様上 204 はボディを持ちません。 Content-Length は「ボディの長さ」を表すヘッダーなので、 ボディが存在しない応答に付けるのは矛盾です。 一部のクライアントやプロキシが混乱します（304 も同様）。
